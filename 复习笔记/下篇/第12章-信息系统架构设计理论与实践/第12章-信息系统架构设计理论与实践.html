二、知识点笔记

12.1.1～12.1.3 信息系统架构概念、发展与定义

信息系统架构（Information System Architecture，ISA）关注系统组成部分之间、系统与业务之间、系统与技术之间的关系。现代信息系统架构有两个层次：概念层次包含艺术、科学、方法和建设风格；物理层次是架构工作形成的物理结构及相互作用结果。

教材原文：软件或计算机系统的信息系统架构是该系统的一个（或多个）结构，而结构由软件元素、元素的外部可见属性及它们之间的关系组成。

⭐【重点】【高频考点】定义抓住三个词：元素、外部可见属性、关系。外部可见属性是其他元素可以依赖的假设，如提供的服务、性能特征；类的私有字段、函数内部算法等纯内部实现细节不属于架构。

信息系统架构的三要素与抽象边界
理解要点必须掌握的含义易混点
多结构不同结构分别传达模块、运行、部署等方面信息，单个结构不能代表完整大型架构架构不是一张部署图
架构与文档任何软件都有架构，但不一定有架构文档；文档可能过时有文档不等于文档反映了真实架构
静态与动态静态关注大粒度总体结构；动态关注关键行为的共同特征不只是「有哪些模块」
基础性与决策解决关键重复问题，包含影响深远、修改代价高的决策架构师水平也是约束，重大决策应评审
举例：订单服务对外承诺「提交订单后 2 秒内返回订单号」属于外部可见属性；它内部用哪种排序算法整理临时数据，通常不是架构关注点。
发展节点核心贡献
20 世纪 80 年代中期，John Zachman引入信息系统架构框架，从信息、流程、网络、人员、时间、基本原理六个视角分析企业
1999 年，美国联邦 CIO 委员会公布联邦企业架构框架，协调公共业务流程、技术引入、信息流和系统投资
1995 年，TOGAF 发布以美国国防部 TAFIM 为基础，形成开放、迭代、可复用架构资产的企业框架

架构受干系人、开发组织、架构师经验和技术环境影响，也会反作用于组织分工、目标和后续需求，形成架构商业周期。

12.2.1 架构风格

教材原文：信息系统架构风格是描述某一特定应用领域中系统组织方式的惯用模式。架构风格定义了一个系统家族，即一个架构定义一个词汇表和一组约束。

通俗地说，架构风格就是某类系统反复使用的「组织套路」：规定有哪些构件/连接件，以及它们怎样组合。它支持架构级大粒度复用，但选择必须结合项目特点。

通用风格代表形式一句话识别
数据流批处理序列、管道/过滤器数据依次经过处理步骤
调用/返回主程序/子程序、面向对象、层次结构一方调用，另一方执行并返回
独立构件进程通信、事件系统构件通过消息或事件协作
虚拟机解释器、基于规则的系统构造执行语义或规则的环境
仓库数据库、超文本、黑板系统围绕共享数据中心协作

12.2.2 信息系统架构分类

⭐【重点】物理结构看硬件资源的空间分布，逻辑结构看功能子系统的综合体，二者分类维度不同。

对比项集中式结构分布式结构
资源配置软件、数据、设备集中；多终端共享主机也属集中式网络连接不同地点的软硬件和数据，可统一管理，也可本地独立运行
优点便于管理、资源利用率较高按需配置、扩展方便、应变能力强；单结点故障一般不致全系统停止
局限规模扩大后维护困难；主机故障易形成单点风险标准不易统一、协调困难、整体资源规划管理复杂
典型形态单机、多用户主机终端一般分布式、客户机/服务器；已成为主流
逻辑结构综合综合对象例子
横向综合同一管理层次的多种职能运行控制层的人事和工资子系统一体化
纵向综合同一职能的不同管理层次工厂会计系统与公司会计系统贯通
纵横综合信息模型和处理模型建公共数据库、统一处理系统，提取通用模块
物理结构对比与逻辑结构综合

⭐【易错】各子系统单独性能优良，不保证整体性能优良；必须统一规划子系统间关系，强调整体协调。

12.2.3 信息系统架构的一般原理

ISA 要在企业战略、业务、组织、管理和技术之间建立多维、分层、集成、开放的体系。其柔性来自把系统拆成「组成成分 + 成分关系」，识别相对稳定部分，在稳定部分支撑下重组易变部分，以较小改动适应环境。

举例：电商的订单、客户、商品等核心概念相对稳定，促销规则变化较快；把促销规则独立配置，就不必每次活动都重写订单核心。

12.2.4 四种常用架构模型

模型核心特征典型适用与提醒
单机应用独立运行于一台物理机，可含多进程/多线程架构形态简单不等于业务算法简单，如 CAD、图像处理软件
两层/多层 C/S（含 MVC）请求—响应分工，逐层分离界面、业务与数据两层偏胖客户端；多层提升伸缩性、并发和隔离性
SOA 与多服务集合多个能独立提供完整功能的应用以消息/RPC 协作服务是广义业务功能单元，不是某个操作系统守护进程
企业数据交换总线以连接器作为公共通道，接收并分发数据、请求、回复成熟总线偏实时交易；可靠的大数据量传输常需单独设计

两层、三层、B/S 与多层 C/S：两层常将界面和业务逻辑集成在客户端，后台提供数据库服务；三层把业务处理独立出来；B/S 采用浏览器这一通用客户端；四层常见为浏览器、Web 服务器、中间件/应用服务器、数据库服务器。

两层、三层、B/S 与多层 C/S 架构对比

⭐【高频考点】B/S 本质是采用通用客户端界面的三层 C/S，浏览器与 Web 服务器仍基于 TCP/IP，只是在应用层用 HTTP 标准化。多层中间件的三大价值：扩展并发与伸缩性、转发请求/处理业务逻辑、隔离 Web 服务器与数据库以提高安全性。

三层 C/S 前后台通信可基于 Socket、自定义消息、RPC、CORBA/IIOP、Java RMI、J2EE JMS、HTTP 等；HTTP 不是面向对象结构，对象数据需平面化后传输。

MVC 角色职责教材中的典型层次映射
View（视图）图形化展示处理结果浏览器/表示相关部分
Controller（控制器）接收请求，连接不同模型和视图Web 服务器相关部分
Model（模型）数据或业务逻辑、持久化应用逻辑及数据部分
MVC 的请求、处理与页面形成过程

MVC 的关键是视图与模型代码分离，控制器负责协调；按业务逻辑是否再独立成服务，可对应三层或四层体系。

对比多层单点应用SOA 多服务结构
对外边界各层共同组成一个完整应用，去掉关键层就不能工作每个服务本身是可独立提供完整功能的应用
协作范围应用内部各层协作多个独立应用之间协作
通信本质预定义协议、请求/回复消息机制或远程过程调用（RPC）

Web Service 是 SOA 在 Web 应用之间的典型实现，常通过 SOAP、WSDL 开放内部服务，但不能把 SOA 等同于 Web Service。

12.2.5 企业信息系统总体框架

⭐【重点】【高频考点】总体框架的四部分与管理金字塔对应；业务系统和应用系统同在第二层。

组成管理层次核心作用
战略系统第一层，战略管理高层决策支持与企业战略规划；向业务系统提重组要求、向应用系统提集成要求
业务系统第二层，战术管理对业务过程/活动建模，以 BPR 优化流程，识别相对稳定数据
应用系统第二层，战术管理用 TPS、MIS、DSS、ES、OAS 等软件实现业务控制并提高运行效率
信息基础设施第三层，运行管理提供数据、技术和管理平台，支撑应用、战略及业务重组
企业信息系统总体参考框架

企业信息基础设施（EII）分三类：技术基础设施（计算机、网络、系统/支持软件、交换协议）、信息资源设施（数据、交换标准、处理方法）、管理基础设施（组织、人员分工、制度）。一般而言信息资源较稳定，技术和管理变化较多，但每类内部都有稳定与易变部分，不能绝对化。

12.3.1 TOGAF 与 ADM 架构开发方法

TOGAF 是 The Open Group 制定的开放企业架构框架，目标是统一沟通语言、避免专有方案锁定、节约资源并提高投资回报。其核心思想包括模块化架构、内容框架、扩展指南和适配不同架构风格。

TOGAF 9 六组件记忆要点
架构开发方法（ADM）核心，开发企业架构的分步方法
ADM 指南和技术应用 ADM 时可采用的指南与技术
架构内容框架工件元模型、架构构建块（ABB）、交付成果
企业连续体和工具对架构输出分类、存储，支持资产复用
TOGAF 参考模型技术参考模型 TRM、集成信息基础设施参考模型 III-RM
架构能力框架建立架构实践所需组织、流程、技能、角色和职责
TOGAF 能力框架与六个组件

企业连续体体现从基础架构、通用基础架构、行业架构到组织特定架构的演进；ADM 指导演进，资源库提供可复用资产，ADM 的新交付物又持续回填资源库。

⭐【重点】【高频考点】ADM 十个阶段中，需求管理位于中心，准备阶段和 A～H 构成迭代过程。

阶段主要活动与高频交付物
准备阶段建团队、定组织范围与治理框架、选并剪裁框架和工具、定义架构原则；形成资源库雏形和架构工作要求书
A 架构愿景定范围、约束、干系人和业务需求，评估能力与风险，形成愿景、工作说明书和计划并获批
B 业务架构描述基线/目标业务架构，差距分析；关注组织、目标、角色等静态特征和流程、功能、服务等动态特征
C 信息系统架构数据架构定义所需数据源和类型；应用架构定义处理数据、支撑业务的应用；两者可顺序或并行
D 技术架构将应用组件映射为硬件、软件、通信技术组件，形成基线/目标技术架构并做差距分析
E 机会及解决方案合并 B～D 差距，识别工作包和项目、过渡架构，决定制造/购买/重用等途径并评估依赖与优先级
F 迁移规划做业务价值、成本、绩效和风险分析，形成详细实施迁移计划、路线图和架构契约
G 实施治理签署架构契约，监督实施、开展合规审查，确保部署方案符合目标架构
H 架构变更管理持续监测基线和业务价值，受控处理技术、业务及经验教训引发的变更，必要时启动新循环
需求管理贯穿所有阶段，识别、存储、排优先级、跟踪变更及影响，维护需求基线和需求库
ADM 全生命周期：准备、A～H 与中心需求管理
助记：「预备愿景起，业信技奠基；机会迁移治，变更需求续」——业务、信息系统、技术是 B/C/D，机会、迁移、治理、变更对应 E/F/G/H，需求贯穿始终。

⭐【易错】B、C、D 的共性步骤是「基线架构 → 目标架构 → 差距分析」；E 才开始直接关注实施，G 是实施中的架构监督，H 是持续变更管理，不要混为一谈。

ADM 的三级迭代：整体迭代（完成一轮进入下一轮）、阶段间迭代（如技术架构返回业务架构）、阶段内迭代（阶段内部活动反复细化）。架构范围由企业自己确定，从四个维度限定：

范围维度要回答的问题
企业范围或焦点覆盖哪个组织、业务或合作联盟
架构领域是否覆盖业务、数据、应用、技术全部四域
详述垂直范围或级别细化到第几层，与系统设计的边界在哪里
时间周期愿景覆盖多久，需要哪些中间目标架构

12.3.2 信息化总体架构方法

信息化是培育、发展以智能化工具为代表的新生产力并造福社会的历史过程。国家信息化体系六要素：信息资源、信息网络、信息技术应用、信息技术和产业、信息化人才、信息化政策。

信息化完整内涵包括信息网络体系、信息产业基础、社会运行环境、效用积累过程；常见平台包括知识管理、日常办公、信息集成、信息发布、协同工作、公文流转、企业通信七类。教材归纳的信息化特征为：易用性、健壮性、平台化/灵活性/拓展性、安全性、门户化/整合性、移动性。

⭐【重点】数据导向与流程导向不是互斥选型，而是互补视角。

对比项数据导向架构流程导向架构
关注中心数据对象及关系、数据模型和质量端到端流程整合及流程变化适应度
切入路径主题域 → 业务对象 → 对象关系 → 概念/逻辑/物理模型价值链 → 流程分解 → 业务组件 → 服务识别与流程编排
典型支撑数据中心、BI、主数据管理 MDMSOA、服务组合、流程服务
单独使用的风险后续仍需管理数据产生、变更、废弃流程可能只有接口元数据，缺完整数据模型，质量治理难落地

SOA 可帮助 MDM 做数据收集、分发和路由；MDM 的统一数据视图和数据质量能力又支撑 SOA 组合服务。

生命周期阶段回答的问题与主要成果
系统规划是否建设、建什么；初步调查、可行性研究，形成可行性报告和系统设计任务书
系统分析做什么；详细调查现行流程，建立新系统逻辑模型，形成系统说明书
系统设计怎么做；把逻辑模型转为物理方案，分总体/详细设计，形成系统设计说明书
系统实施把设计落地；购置安装、编程调试、培训、数据转换、系统转换和测试
系统运行和维护运行记录、评价、修改和效益评估，直至由新系统替代
信息化建设五阶段生命周期

⭐【高频考点】三种总体规划方法的区分：

方法核心路径优势与局限
关键成功因素法 CSF组织目标 → 识别关键成功因素 → 性能指标 → 关键信息集合/数据字典 → 开发优先次序抓主要矛盾、重点突出，最利于确定管理目标；关键因素随组织和时期变化
战略目标集转化法 SST使命、目标、战略等战略集合 → 转化为 MIS 战略目标反映多方要求、较全面少疏漏；突出重点不如 CSF

CSF、SST、BSP 三种规划方法路径对比

12.4.1 价值驱动的体系结构

系统存在的目的是为干系人创造价值。价值模型把「想要什么」和环境限制联系起来，帮助架构师优先解决最有价值的架构挑战。

价值驱动因素含义例子
价值期望值对功能、质量及不同质量级别实用性的期望高峰期提交订单仍需 2 秒响应
反作用力实际环境中实现期望的难度请求量放大百倍、数据同步开销
变革催化剂使期望或结果发生变化的环境事件/限制大促开始、法规或部署地点变化
从价值驱动因素到体系结构策略

反作用力与变革催化剂合称限制因素。体系结构挑战是限制因素使价值期望更难满足；确定优先级时权衡重要性、程度、后果、隔离。最终策略从组织、操作、可变性、演变四方面给出简短、稳定且可理解的指导原则。

12.4.2 Web 服务在 HL7 上的应用

HL7 名称中的「第七层」指 OSI 应用层。HL7 V3 以参考信息模型（RIM）为公共静态模型，将领域模型逐步精化并与消息类型结合，生成 XML Schema（XSD）。应用间通过消息交换协作，触发事件启动一次交互，应用程序角色表示发送/接收职责，Storyboard 汇集用例叙述、角色、消息类型与交互顺序。

HL7 消息开发框架：活动、模型与规格
HL7 核心制品作用
RIM 参考信息模型提供卫生保健领域公共静态信息模型
UCM / IM分别描述用例和交互关系
HMD 层次消息描述描述消息的层次结构
ITS 实现技术规格规定具体实现技术和消息格式

⭐【重点】参考体系结构把应用内部功能分为业务逻辑与 Web 服务适配器：发送端业务逻辑生成 HL7 XML 消息；适配器读取封装、配置并生成 SOAP 消息，再交给 Web 代理传输。接收端适配器验证 SOAP、拆出并校验 HL7 消息、处理通信确认，再交业务逻辑验证业务规则并按需返回应用层确认。

HL7 Web 服务发送/接收参考体系结构

开发适配器五步骤：消息和数据类型设计 → 适配器模式选择 → WSDL 契约开发 → 生成 Stub/代理 → 开发适配器业务逻辑。WSDL 中，端口指定服务位置和绑定，端口类型表示接口，操作定义输入/输出，消息格式基于 XSD 类型。

12.4.3 以服务为中心的企业整合

航空公司案例的痛点具有代表性：主机 Information Hub 难向开放系统开放、事件点到点流转导致强耦合、跨系统业务协作硬编码导致自动化成本高和复用差。

案例步骤关键活动本章示范结果
业务环境分析比较多类航班流程，找共享业务活动把机位、卸货、装货、推出检查抽象为可复用服务
服务建模建业务组件、服务与流程模型Flight Management 输出 Retrieve Flight BO；Ramp Control 输出流程和检查服务
IT 环境分析调研外围应用、接口、交互类型和数据格式识别乘务、机务、订票、航班调度四类交互
高层架构设计将服务映射为信息、流程、事件、人工、传输等服务以 ESB 和适配机制连接新旧系统，降低耦合
开发与演进选择当前实现方式，保持服务契约稳定人工服务未来可替换为自动服务，流程无需整体重写

Retrieve Flight BO 是信息服务，聚合乘务、机务、订票数据形成粗粒度 Flight BO；Ramp Coordination 是流程服务，由 BPEL4WS 执行并编排共享活动；航班到达由事件服务经 MQ、Message Broker 和 JMS 发布/订阅分发；人工检查是 Staff Service。

以服务为中心的企业整合：流程编排与 ESB 接入

⭐【案例启示】粗粒度业务对象提高旧系统连接的通用性；ESB 发布/订阅替代点到点事件连接；流程编排复用业务活动；服务可替换性支持平滑演进。案例答题要把这些机制对应到题干痛点，而不是罗列产品名。

三、重点与易错点

#考点必须记住的结论易错提醒
1ISA 定义元素 + 外部可见属性 + 关系；架构可包含多个结构纯内部实现细节不属于架构，文档不等于架构本身
2物理与逻辑结构物理看空间分布；逻辑看功能子系统综合多终端共享主机仍是集中式
3集中式与分布式分布式扩展和容错较好，但标准协调与整体管理更难分布式不等于没有故障或无需统一管理
4三种逻辑综合横向同层跨职能；纵向同职能跨层；纵横综合信息与处理模型横向、纵向的分类维度不要对调
5两层 C/S前台界面与业务逻辑常集成，后台数据库，偏胖客户端不是「客户端只负责展示」
6B/S 本质通用浏览器作客户端的三层 C/S，仍基于 TCP/IPHTTP 标准化不等于脱离 TCP/IP
7多层中间件伸缩并发、请求转发/业务处理、数据库访问隔离中间件不是简单增加一台 Web 服务器
8MVC视图展示、控制器协调、模型承载数据或业务逻辑MVC 目标是视图与模型分离，不是三者完全无交互
9SOA 与多层应用SOA 服务是可独立提供完整功能的应用，应用间靠消息/RPC不要把层内服务、守护进程与 SOA 服务混同
10数据交换总线连接器负责接收分发；实时交易与大数据量可靠传输常分别设计总线不天然包办所有批量传输需求
11企业总体框架战略第一层；业务与应用同第二层；基础设施第三层业务系统和应用系统不是上下两层
12TOGAF 组件ADM 是核心，另有指南技术、内容、连续体工具、参考模型、能力框架TRM 与 III-RM 属参考模型组件
13ADM 十阶段准备、A～H、需求管理；需求管理贯穿中心不要漏准备阶段或把需求管理算作 A～H 之一
14B/C/D 与 E/F/G/HB/C/D 做基线、目标、差距；E 实施规划，F 迁移，G 实施治理，H 变更实施治理不是迁移规划，变更管理不是需求管理
15ADM 迭代与范围整体、阶段间、阶段内三级迭代；范围四维度ADM 不替企业自动确定架构范围
16生命周期分析回答做什么、形成逻辑模型；设计回答怎么做、形成物理模型系统说明书属分析，系统设计说明书属设计
17CSF/SST/BSPCSF 抓关键重点；SST 战略集转化全面；BSP 上下结合、过程/数据矩阵BSP 不是纯粹自底向上规划
18数据与流程导向数据导向重模型质量，流程导向重端到端整合；MDM 与 SOA 互补不是二选一，流程中传递的仍是数据
19价值驱动期望值、反作用力、变革催化剂；后两者为限制因素优先级要看重要性、程度、后果、隔离
20HL7 与企业集成适配器处理 SOAP/传输确认，业务逻辑处理 HL7 业务规则；ESB 事件解耦HL7 标准化消息不等于直接给出完整应用实现

1. D。架构强调元素、外部可见属性和关系，纯内部算法实现通常被抽象掉。
