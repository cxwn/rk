二、知识点笔记

19.1 传统数据处理系统存在的问题

数据从 MB/GB 增长到 TB/PB 后，单靠关系数据库难以承载。传统优化是在原有架构上不断「打补丁」，能缓解局部压力，却把路由、复制和运维复杂度推给应用。

演进手段解决的问题仍未解决/新增的问题
Web 与数据库间加异步队列削峰缓冲，工作层可每次批量取消息消费跟不上仍会积压；数据库最终仍可能过载
增加多个工作处理层提高消息消费并发数据库再次成为瓶颈
Hash 水平分区、分库分表分散单库存储与访问压力应用须知道 key 到分区的路由和 schema
扩容后 reshard重新均衡分区数据迁移、地址与代码更新复杂；在线迁移易写错分区
Master-Slave 读写分离分担读压力、提高读扩展能力复制、分区、分布式查询仍需应用协调
Hadoop MapReduce 管道用不可变主数据和批视图支撑海量计算批任务完成前新数据已进入，视图容易过时
传统数据处理架构演进与瓶颈
  • 根本短板：数据库并不天然替应用处理分区、复制和分布式查询；仅靠备份也不能限制人为错误造成的破坏。
  • 架构启示：大数据系统应把容错、扩容、低延迟查询和可追溯作为内生能力，而非外围脚本堆叠。

19.2 大数据处理系统架构分析

19.2.1 三项挑战 ⭐【重点】

挑战核心含义记忆抓手
非结构化/半结构化处理文本、图像、社交与电商数据难直接套用二维表；一种表示只呈现数据的一个侧面数据「怎么表示、怎么挖掘」
复杂性与不确定性建模高维、多变、强随机，需研究统一描述、转换原则及知识度量知识「怎么建模、怎么评价」
数据异构与决策异构数据来源和结构多样，决策者经验、情境、偏好也不同数据知识「怎么进入决策」
  • 一次挖掘：从数据中提取结构化「粗糙知识」；二次挖掘：把粗糙知识与经验、常识、情境、偏好等主观知识结合，形成可支撑决策的「智能知识」。
  • 举例：一次挖掘发现「某商品雨天销量上升」，二次挖掘再结合当地天气、库存和经理经验，决定「是否补货、补多少」，后者才直接服务决策。
助记：三大挑战＝「非结构、难建模、双异构」；知识跃迁＝「一次出粗糙，二次融主观」。

19.2.2 八项架构特征 ⭐【高频考点】

特征必须理解的含义
鲁棒性和容错性机器宕机、程序 Bug、人为误操作发生时仍行为正确并能恢复；人为容错尤其重要
低延迟读取和更新在鲁棒前提下支持毫秒至数百毫秒级读写
横向扩容 Scalable负载增长时增加机器维持性能，优先 scale out 而非单纯 scale up
通用性 General能支持金融、社交、电商等多类应用
延展性 Extensible能添加新功能，并支持大规模迁移
即席查询 Ad Hoc用户可按临时组合条件查询，而非只能跑固定报表
最少维护 Minimal Maintenance用简单机制和算法降低底层复杂度、错误率与繁重操作
可调试性 Debuggable每个结果值都能追踪来源并解释其产生过程
助记：「鲁、低、横、通、延，即、少、调」——鲁棒低延，横向通用可延展，即席少维护可调试。

19.3 Lambda 架构

19.3.1～19.3.2 定义与场景

教材原文：Lambda 是用于同时处理离线和实时数据的、可容错的、可扩展的分布式系统，具备强鲁棒性，提供低延迟和持续更新。
  • 提出者是 Storm 之父 Nathan Marz；核心手段是整合离线与实时计算，融合不可变性、读写分离、复杂性隔离。
  • 机器学习可利用其处理后的数据做模式识别；物联网传感器则是典型的海量实时输入源。
  • 速度层追求最新数据的低延迟视图，允许暂时近似；后续批视图覆盖相同数据后，系统达到最终精度。

19.3.3 三层体系结构 ⭐【重点】【高频考点】

Lambda 三层架构
层次输入与职责输出/特点
Batch Layer 批处理层管理全量主数据集，预计算业务查询Batch View；精准、全量，但时延高
Speed Layer 加速层/流处理层只处理最近增量数据流，持续增量更新Real-time View；低延迟，可能暂时不精确或不完整
Serving Layer 服务层响应查询，合并两类视图并建立必要索引最终查询结果；要求随机读、批量写、可伸缩、容错
助记：「批全量、速增量、服合并」；「批求准确速求快，服务对外统一看」。

主数据集三属性：数据是原始的、不可变的、永远真实的。它保存事实，不随视图算法错误而被覆盖。

1. Monoid（幺半群）与视图合并⭐【易错】

  • 关键性质是结合律：(a+b)+c=a+(b+c)，因此可分组并行计算，再合并部分结果；部分结果还能复用。
  • 加法、求和满足结合律；平均值不能直接合并两个平均值，但可拆成「总和与计数」分别合并，最后再相除。
  • 举例：两班平均成绩不能直接取平均；应分别汇总「总分、人数」，相加后用「全部总分÷全部人数」得到总平均。
Monoid 结合律与分布式复用

2. 批视图预计算与实时视图滚动更新

  • Batch Layer 按业务可能需要的有限查询，在全量数据上预先构建 View；查询时直接读取或简单加工，避免每次全量重算。
  • Speed Layer 接收新数据便更新 Real-time View；当新的 Batch View 已覆盖这些增量数据，旧实时视图可丢弃。
批处理预计算与加速层增量视图

3. 服务层合并与复杂性隔离

  • 查询函数满足 Monoid 性质时可直接合并两类结果；不满足时先拆成可合并的中间结果，或按明确业务规则合并。
  • 新数据同时进入批、速两条链路，实时误差会由后续全量重算修正，体现教材所述的最终一致性。
  • 离线与实时拆开，把高复杂度的增量算法隔离在 Speed Layer，提高整体鲁棒性；代价是两套计算逻辑。
服务层合并 Batch View 与 Real-time View

角色教材常见选型选择理由
主数据集/分布式存储Hadoop HDFS通用硬件、高容错、高吞吐，适合大规模数据集
批处理与批视图MapReduce、Hive全量离线计算，构建可查询 Batch View

19.3.5～19.3.6 优缺点与相关模式

方面内容
优点容错好，可修复算法后重算；批层支持灵活查询；各层可分布式扩展；新增视图较容易
缺点全场景覆盖编码开销大；具体场景反复离线重训收益未必高；重新部署和迁移成本高
与事件溯源相同点都以事件/事实为核心，业务视图由事实产生；出错可定位事件并重算恢复
与 CQRS 相同点写入负责把数据加工成 View，查询直接读 View，属于读写职责分离
助记：Lambda 优点「容错、灵活、好扩、易加视图」，代价牢记「两套代码、两套系统、迁移重」。

19.4 Kappa 架构

19.4.1 数据本质与不可变存储 ⭐【重点】

  • 数据系统可概括为「数据 + 查询」。数据的 When 是发生时间，决定全局先后；What 是数据事实本身，过去发生的事实不可更改。
  • 因而逻辑上只读取或追加新事实；Update/Delete 也可用一条新的事实记录表达，而不是抹掉历史。
  • 不可变存储只需追加，避免更新索引的复杂性；原始错误数据仍在，修复算法后可按时间顺序重新计算，不会因覆盖而失去恢复依据。
  • 举例：账本写错不撕掉原页，而是追加一张更正单；月底按单据时间顺序重算，既能得到正确余额，也能解释每笔结果从何而来。

19.4.2～19.4.3 体系结构与重放切换 ⭐【高频考点】

Kappa 由 Jay Kreps 提出，删除独立 Batch Layer，以一条流计算链路处理实时与历史数据。历史日志可长期保存；需要离线分析或算法升级时，再经消息队列重放进入同一流引擎。

Kappa 单流链路与历史重放

版本切换四步：

  1. 设置日志保留期，使其覆盖需要重算的历史区间。
  2. 启动作业新实例，将 Log Offset 置 0，从头计算并写入新视图。
  3. 新视图追平旧视图后，应用切换读取新视图。
  4. 停止旧实例并删除旧视图。

19.4.4～19.4.5 优缺点与变形

方面Kappa 的特点
优点实时与离线共用一套代码和口径；维护较简单；无须合并批、实时两类视图；历史查询可重放
缺点 1长期日志占用消息中间件，海量回溯消耗大且存在性能瓶颈
缺点 2多实时流关联依赖流引擎能力，乱序与算法逻辑可能导致数据丢失
缺点 3删除独立离线模块，也失去其稳定可靠、擅长大规模批处理的优势
变形核心改进仍有限制
Kappa+用 HDFS/Hudi 保存仓库数据，流框架直接读实时与历史分区完成 backfill依赖分区、窗口与 watermark 等设计
混合分析系统Kafka + Flink 后接 ElasticSearch，增强热点数据检索分析ES 只适合合理量级的热点数据，不能覆盖全部批分析
Kappa+ 与混合分析系统

19.5 Lambda 与 Kappa 的对比和选择 ⭐【重点】【高频考点】

对比维度LambdaKappa
系统/代码批、实时两套系统与代码一套流式系统与代码
开发维护成本高，部署测试和口径一致性工作多相对低，算法修改只改一处
计算开销持续运行批与实时计算，教材认为较大平时单流，必要时才全量重算，教材认为相对较小
实时性能满足；实时视图与批视图结合能满足；直接由流处理产出结果
历史数据能力批式全量吞吐大，能力强流式全量吞吐相对低，受日志保留和回溯能力制约
典型优势场景海量历史探索分析 + 实时查询；批流逻辑无法统一增量时序数据、天然时间窗口、统一流式代码
Lambda 与 Kappa 设计选择

设计选择看四项：业务与技术要求、复杂度、开发维护成本、历史数据处理能力。教材明确说计算开销虽有差别但不作为主要选择因素。

  • 依赖 Hadoop/Spark/Storm，或必须先离线训练模型再实时验证，选 Lambda。
  • 偏好 Flink、希望一份代码同时承担实时和回溯，且数据规模与重放资源可控，选 Kappa。
  • 频繁修改算法时 Lambda 要改两套；长期海量历史分析时 Kappa 的消息缓存和回溯压力更突出。
助记：「历史重、批流异，Lambda；增量流、求一统，Kappa」；选型四看「业务、复杂、成本、历史」。

19.6 大数据架构设计案例分析

19.6.1 奥运视频平台：Lambda 同时满足秒级与历史统计

  • 当日概览要求秒级刷新在线人数、浏览量、播放次数等，采用 Spark Streaming 增量计算；赛事回顾要求自定义时段的历史峰值与排行，采用不可变主数据和离线批算。
  • 采集 PC/App/TV 数据，实时链路经 Nginx、Flume、Kafka，离线链路经 Sqoop；存储含 HDFS、HBase、MemSQL；计算分离线、实时、合并三部分，最终服务当日概览与赛事回顾。
某网奥运 Lambda 平台分层架构

19.6.2 广告平台：把工作从查询端前移 ⭐【案例高频】

版本主要做法暴露瓶颈/下一步改进
第一版Hive/Spark 离线结果入 MySQL，Spark Streaming 实时结果入 Redis，Java 查询时多源关联合并Java 服务逻辑重、性能差；第三方曝光等数据不够实时
第二版定时同步第三方报表，离线预先 join 并导出结果Java 压力下降，但 Redis 键关联聚合成为瓶颈；离线依赖链长
第三版单一 MySQL 统计表，当天行存实时、历史行存离线；下单处理时提前完成业务关联服务层只读一表；将关联工作前移到数据收集/计算阶段
广告平台 Lambda 三版演进

案例结论：标准分层不是终点；当服务层成为瓶颈，应把可预先完成的 join、聚合和维度关联前移，让查询端保持简单。

三、重点与易错点

#考点必须记住的结论易错提醒
1传统架构根因队列、分区、读写分离只是缓压，应用复杂性持续上升队列不能根治数据库过载
2八项特征容错、低延迟、横扩、通用、延展、即席、少维护、可调试横向扩容是加机器，不是只升级单机
3二次挖掘粗糙知识融合主观知识形成智能知识一次挖掘不等同最终管理决策
4Lambda 提出者Nathan MarzKappa 才是 Jay Kreps
5Batch Layer管全量主数据并生成 Batch View，准确但慢不负责毫秒级增量刷新
6Speed Layer处理最近增量并更新 Real-time View，快但可暂时近似不是长期保存全量主数据之处
7Serving Layer合并批/实时视图并对查询提供低延迟访问不是重新执行全量计算的层
8主数据三性原始、不可变、永远真实不可变不等于不能追加更正事实
9Monoid结合律支持分组并行、部分结果合并与复用平均值须拆成总和与计数，不能直接平均平均值
10最终精度后续批视图覆盖并纠正实时近似结果不代表实时视图永远精确
11Lambda 成本两套代码、两套系统，维护与迁移成本高查询灵活不代表实现简单
12Kappa 本质删除独立批层，用同一流链路处理实时与历史重放不是 Lambda 的全场景替代品
13Kappa 切换新实例从 Offset 0 重放，新视图追平后切换，再停旧删旧不能直接覆盖唯一生产视图
14Kappa 短板长周期日志存储、海量回溯、多流关联压力大一套代码不等于资源消耗一定低
15Kappa+HDFS/Hudi 支撑直接 backfill，减少长期日志和回拷 MQ仍需处理时间分区、窗口和 watermark
16混合分析ES 补强热点检索，是折中而非全量批分析替代不要把 ES 当作无限容量历史仓库
17选型因素看业务技术、复杂度、维护成本、历史能力按教材，计算开销不列为主要选择因素
18广告演进将 join、聚合、关联从服务查询端前移分层正确不代表查询端可以无限复杂

五、疑问与查漏补缺

  • 大纲中的「定义、范围」：教材 19.2 更侧重挑战与八项特征，没有另起严格定义；复习时可用「数据 + 查询」及 Lambda/Kappa 的分布式容错、低延迟、可扩展目标补全理解。
  • 教材 19.3.3 加速层首句易误读：「对加速层批处理视图建立索引」上下文不一致；按三层职责，应理解为实时层维护实时视图，服务层为查询视图建立索引。
  • 教材 Monoid 平均值表述有笔误：应拆为「总和÷计数」，不是「分母除以分子」；合并时先分别求和，再做除法。
  • 教材 When 示例中的加法不成立：先 +2 后 +3 与先 +3 后 +2 结果相同；说明顺序重要性可改用「先 ×2 再 +3」与「先 +3 再 ×2」。
  • Hadoop 与 HDFS 要区分：HDFS 是分布式文件系统，Hadoop 是包含存储、计算等能力的生态/平台，答题不要把二者完全等同。
  • 与第 6、8 章衔接：分库分表、读写分离承接数据库设计；容错、可伸缩、低延迟和可维护性可结合质量属性与架构评估作答。
  • 实践边界：教材按当时技术背景比较开销，现实选型还需验证 exactly-once、乱序处理、状态后端、保留周期、存储成本与团队能力，但考试作答先以教材结论为准。
