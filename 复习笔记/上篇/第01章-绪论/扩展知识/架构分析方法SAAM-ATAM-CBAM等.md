## 二、一个故事串起六种方法

某团队要做一个「校园外卖平台」，六种方法分别在不同时刻登场：

1. **SAAM——设计评审时问「以后好不好改」**：评审会上，大家把未来可能的需求写成场景逐一走查。「商家修改店铺头像」现有架构直接支持，是**直接场景**；「新增一种支付方式」要改动订单、支付、对账等 5 个模块，是**间接场景**。间接场景牵连越广，可修改性越差。
2. **ATAM——质量属性打架时找「权衡」**：安全组要求支付数据全程加密，性能组担心响应变慢。评估发现「加密级别」同时影响安全性和性能，是**权衡点**；「数据库连接池大小」微调就明显影响吞吐量，是**敏感点**。评估产出风险清单，而不是一个总分。
3. **CBAM——拍板之前先「算账」**：策略 A「引入缓存」预计投入 10 万人天成本、质量收益折算 30 万；策略 B「全面升级加密」投入 5 万、收益折算 10 万。A 的 ROI（投资回报）更高，预算内优先做 A。
4. **SBAR——接手老系统时「再工程」**：学校原有的食堂收银系统没有文档、急需改造接入校园平台。团队先从代码逆向**发现**实际架构，再按新业务场景**重构**出目标架构，最后**评估**重构方案是否满足质量要求。
5. **ALPSM——想提前知道「将来维护要花多少工」**：针对维护场景「新增一种支付方式」，方案一（支付逻辑写死在订单流程里）预测要改 10 个类、约 15 人天；方案二（插件式支付接口）只需新增 1 个插件、约 2 人天。设计阶段就用数据比较可维护性。
6. **SAEM——把「用户关心的」和「开发者能测的」连起来**：用户说「这系统以后要好改」（**外部质量属性**：可修改性），开发者就把它落实为「模块耦合度、内聚度」（**内部质量属性**）的度量，用内部度量预测外部质量。

## 三、六种方法逐一详解

### 1. SAAM：软件架构分析方法（Software Architecture Analysis Method）

- 出身：SEI（卡耐基梅隆大学软件工程研究所）提出，是**最早**形成文档并广泛使用的架构分析方法 ⭐【高频考点】。
- 核心问题：**架构对各类场景（尤其是修改场景）的支持程度如何？**最初主要评估**可修改性**，后扩展到可移植性、可扩展性等。
- 关键机制：场景走查。直接场景无需修改即可支持；间接场景需要修改构件或交互。**场景交互评估**还会检查「多个场景是否都要改同一个构件」，暴露耦合集中的地方。
- 一句话类比：交房前的「验收走查」——不是看图纸漂亮不漂亮，而是模拟「以后想砸掉这堵墙改户型」时，要牵连多少地方。
- 考试关键词：最早、可修改性、直接/间接场景、五步（场景开发→架构描述→单场景评估→场景交互评估→总体评估）。
- ⭐【易错】教材明确：SAAM **不考虑已有知识库的可重用性**。

### 2. ATAM：架构权衡分析法（Architecture Tradeoff Analysis Method）

- 出身：SEI 在 SAAM 基础上发展而来。
- 核心问题：**性能、可用性、可修改性、安全性等多个质量属性相互竞争时，架构决策在哪里折中、哪里有风险？**
- 关键机制：
  - **效用树**：树根（效用）→质量属性→属性分类→具体场景（叶子），按「重要性 / 实现难度」用 H/M/L 标优先级，如 (H,M)；
  - **敏感点**：一个或多个构件（或其关系）的特性，对实现某个质量属性至关重要；
  - **权衡点**：**影响多个质量属性的特性，是多个质量属性的敏感点** ⭐【必考定义】；
  - 产出风险点、非风险点清单，而非给架构打总分。
- 一句话类比：装修预算会——「装地暖（舒适）就压层高（空间）」，评估师把每个方案的连带影响摆到桌面上。
- 考试关键词：Tradeoff=权衡、效用树、敏感点/权衡点、用例场景/增长场景/探测场景。

### 3. CBAM：成本效益分析法（Cost Benefit Analysis Method）

- 出身：SEI 提出，**在 ATAM 评估之后开始**，复用其场景与结论。
- 核心问题：**架构策略值不值得做？先做哪个？**——把技术决策变成经济决策。
- 关键机制：为场景分配效用、估算每个架构策略的成本与收益，计算 **ROI = 收益 ÷ 成本**，按 ROI 排序并在预算约束内选择策略。
- 一句话类比：评估完车况（ATAM）之后，再决定「修哪里最划算」——不是修最重要的，而是修**单位投入收益最大**的。
- 考试关键词：Cost Benefit、ROI、基于 ATAM、效用表、场景投票排序。

### 4. SBAR：基于场景的架构再工程（Scenario-Based Architecture Reengineering）

- 核心问题：**已有的遗留系统如何借助场景完成架构再工程（重构/再设计）？**前面三种方法偏「评估设计中的架构」，SBAR 面向「已经存在、需要改造的系统」。
- 关键机制（本章仅列名称，以下为背景补充）：以功能场景和质量属性场景驱动，一般经历**架构发现**（从代码、文档还原实际架构）→ **架构重构**（按场景形成目标架构）→ **架构评估**（验证是否满足质量目标）等活动。
- 一句话类比：老城区改造——先测绘出「现状图」，再按新需求画「规划图」，最后论证规划是否可行，而不是直接推倒重来。
- 考试关键词：Reengineering=再工程、遗留系统、场景驱动。

### 5. ALPSM：架构层次的软件可维护性预测（Architecture Level Prediction of Software Maintenance）

- 出身：由 Bengtsson 与 Bosch 提出（背景了解）。
- 核心问题：**能否在架构设计阶段就预测未来的维护工作量，从而选出「更好养」的方案？**
- 关键机制（背景了解）：编写一组**维护场景**（预计未来会发生的修改），结合架构描述与历史维护数据/专家估计，预测每个场景涉及的构件与工作量，汇总比较。
- 一句话类比：买车前比较「保养成本」——不只看车价，还估算「以后每次换零件要拆多少东西、花多少工时」。
- 考试关键词：Prediction=预测、Maintenance=维护、维护场景、工作量预测。

### 6. SAEM：软件架构评估模型（Software Architecture Evaluation Model）

- 核心问题：**如何把用户眼中的质量与开发者可度量的架构特征联系起来评估？**
- 关键机制：区分两类质量属性并建立映射——
  - **外部质量属性**：用户角度可感知，如可修改性、可移植性；
  - **内部质量属性**：开发者角度决定，如模块化程度、耦合度、可复用性。
  - 内部属性是「因」，外部属性是「果」：通过内部度量预测外部质量。
- 一句话类比：食客只说「菜要好吃」（外部），厨师把它分解为「火候、刀工、新鲜度」（内部）等可操作的指标。
- 考试关键词：Evaluation Model、外部（用户）/内部（开发者）质量属性、度量映射。

## 四、横向对比总表

| 缩写 | 全称 | 中文名 | 核心目标 | 识别关键词 |
| --- | --- | --- | --- | --- |
| SAAM | Software Architecture Analysis Method | 软件架构分析方法 | 评估**可修改性**（最早的方法） | 直接/间接场景、场景交互、五步 |
| ATAM | Architecture Tradeoff Analysis Method | 架构权衡分析法 | 多质量属性之间的**权衡**与风险识别 | 效用树、敏感点、权衡点、三类场景 |
| CBAM | Cost Benefit Analysis Method | 成本效益分析法 | 架构策略的**经济决策**（基于 ATAM） | 成本、收益、效用、ROI |
| SBAR | Scenario-Based Architecture Reengineering | 基于场景的架构再工程 | **遗留系统**的架构重构/再设计 | 再工程、架构发现→重构→评估 |
| ALPSM | Architecture Level Prediction of Software Maintenance | 架构层次的软件可维护性预测 | 设计期**预测维护工作量** | 维护场景、工作量/成本预测 |
| SAEM | Software Architecture Evaluation Model | 软件架构评估模型 | **内外部质量属性**的映射评估 | 外部（用户）/内部（开发者）、度量 |

## 五、演化关系与家族脉络

```text
SEI 主线（重点记忆）：
  SAAM（最早，看可修改性）
    └─→ ATAM（扩展为性能/可用性/可修改性/安全性等多属性权衡）
          └─→ CBAM（在评估结果之上叠加成本效益分析，按 ROI 决策）

补充视角（识记即可）：
  SBAR  ——面向已有系统：基于场景的架构再工程
  ALPSM ——面向未来维护：架构层次的可维护性预测
  SAEM  ——面向质量建模：外部/内部质量属性的映射评估
```

## 六、助记与易错点

> 助记：**SAAM 最早看修改，ATAM 权衡找敏点；CBAM 接着来算账，SBAR 重构旧架构；ALPSM 预言维护量，SAEM 内外两视角。**

⭐【易错清单】

1. **权衡点 ≠ 敏感点**：只影响一个质量属性的是敏感点；**同时影响多个质量属性的敏感点**才是权衡点（加密级别影响安全性与性能，是权衡点；连接池大小只影响性能，是敏感点）。
2. **演化顺序**：SAAM → ATAM → CBAM，CBAM 复用 ATAM 的场景与评估结果，不要记成 CBAM 先于 ATAM。
3. **SAAM 的地位**：题干出现「最早」「形成文档并广泛使用」「可修改性」即指向 SAAM。
4. **SBAR 的适用对象**：是「已有系统的再工程」，不是新系统的架构评估；题干出现「遗留系统、重构、再工程」选 SBAR。
5. **ALPSM 的时间点**：在**架构设计阶段**预测维护工作量，不是系统上线后统计维护成本。
6. **SAEM 的视角**：外部属性=用户可感知，内部属性=开发者决定；不要把「耦合度」说成外部质量属性。
7. **ATAM 的输出**：是风险、非风险、敏感点、权衡点清单，**不是给架构打一个总分**。
